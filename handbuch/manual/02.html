Kapitel 2

Installation und Betrieb

Klausurwerk mit Docker Compose aufsetzen, den Setup-Assistenten durchlaufen, den Runner verstehen und die Anwendung dauerhaft betreiben.

Für Admin

2.1Voraussetzungen und Architektur

Klausurwerk besteht aus drei Containern, die gemeinsam mit Docker Compose gestartet werden:

DienstAufgabe
appPHP 8.3 mit Apache. Liefert Oberfläche und Schnittstellen aus, hängt am Netz des Reverse-Proxys (proxy_network) und am internen Runner-Netz. Hört im Container auf Port 80, auf dem Host standardmäßig auf Port 9030.
dbMariaDB 11.4. Alle Daten (Konten, Klausuren, Antworten, Bewertungen) liegen im Volume db_data.
runnerFührt Java-Code (und versteckte Tests) abgeschottet aus. Hängt nur am internen Netz runner_net ohne Internetzugang und ist von außen nicht erreichbar.

Mindestanforderung: 2 CPU-Kerne und 4 GB Arbeitsspeicher für einen Raum mit etwa 35 Schülern. Für mehrere Räume gleichzeitig erhöhen Sie RUNNER_CPUS, RUNNER_MEM_LIMIT und RUNNER_MAX_PARALLEL. Benötigt werden Docker mit dem Compose-Plugin und ein Reverse-Proxy, der das Netz proxy_network bereitstellt und HTTPS terminiert.

Python und SQL laufen im Browser

Nur Java-Aufgaben belasten den Server. Python (Pyodide) und SQL (SQLite als WebAssembly) rechnen im Browser des Schülers. Die Kapazität des Runners ist deshalb nur für Java-Klausuren und die automatische Vorbewertung in der Korrektur relevant.

2.2Erster Start

  1. Projektordner auf den Server kopieren (oder aus Git klonen) und die Vorlage der Konfiguration kopieren: cp .env.example .env.
  2. In .env die Pflichtwerte setzen: DB_PASS, DB_ROOT_PASS und RUNNER_TOKEN (zum Beispiel mit openssl rand -hex 32).
  3. Das Netz des Reverse-Proxys anlegen, falls es noch nicht existiert: docker network create proxy_network.
  4. Bauen und starten: docker compose up -d --build. Der erste Build lädt Basis-Images und Laufzeiten und dauert einige Minuten.
  5. Im Browser http://localhost:9030 (oder die Adresse hinter dem Reverse-Proxy) öffnen. Beim ersten Aufruf erscheint der Setup-Assistent.
cp .env.example .env # DB_PASS, DB_ROOT_PASS und RUNNER_TOKEN setzen docker network create proxy_network docker compose up -d --build docker compose ps

Der Setup-Assistent

Der Assistent erscheint nur, solange es noch kein Konto gibt. Er fragt nach Vorname, Nachname, Benutzername, E-Mail (für Anmeldecodes), Passwort (mindestens 8 Zeichen), Passwort wiederholen und dem Namen der Schule. Damit wird das erste Admin-Konto angelegt. Danach ist die Seite /setup nicht mehr nutzbar, und Sie landen auf der Anmeldeseite.

Gesund oder nicht?

Prüfen Sie nach dem Start /healthz (antwortet ok, wenn die Anwendung läuft) und /readyz (200, wenn auch die Datenbank erreichbar ist, sonst 503). Beide Adressen funktionieren ohne Anmeldung und eignen sich für Überwachungswerkzeuge.

2.4Reverse-Proxy und HTTPS

Im Betrieb steht ein Reverse-Proxy (zum Beispiel Nginx Proxy Manager, Traefik oder Caddy) vor der Anwendung. Er terminiert HTTPS und leitet auf den Container klausurwerk-app (Port 80) im Netz proxy_network weiter. Wichtig:

  • Tragen Sie die Adresse des Proxys in TRUSTED_PROXIES ein, damit Anmeldedrossel und Audit-Log die echte Adresse der Clients sehen.
  • Die Anwendung setzt strenge Sicherheitsköpfe (Content Security Policy, Cross-Origin-Isolation). Der Proxy darf diese Köpfe nicht entfernen oder überschreiben. Ohne Cross-Origin-Isolation kann Python-input() im Browser nicht auf Eingaben warten.
  • WebSockets sind nicht nötig. Die Live-Ansichten arbeiten mit kurzem Abruf (Polling).
  • Tragen Sie unter Verwaltung › Einstellungen die Öffentliche Adresse ein. Sie steckt im QR-Code der Zugangskarten und in der SEB-Datei. Ohne Eintrag wird die Adresse verwendet, mit der Sie gerade zugreifen, auf dem Server oft localhost, was auf den Karten wertlos ist.

2.5Fertige Images aus der GHCR

Statt lokal zu bauen, kann der Server fertige Images aus der GitHub Container Registry ziehen. Setzen Sie in .env:

APP_IMAGE=ghcr.io/theunknown-0/klausurwerk-app:latest RUNNER_IMAGE=ghcr.io/theunknown-0/klausurwerk-runner:latest

und starten Sie mit docker compose pull && docker compose up -d. Die Images entstehen automatisch über GitHub Actions.

2.6Mailserver und Anmeldecode

Lehrkräfte und Admins können sich zusätzlich mit einem sechsstelligen Anmeldecode per E-Mail absichern (zweiter Faktor). Das funktioniert nur, wenn MAIL_HOST und MAIL_FROM_ADDRESS gesetzt sind. Solange das fehlt, zeigt die Übersicht des Admins einen gelben Hinweis, und Lehrkräfte melden sich nur mit Passwort an.

  1. SMTP-Zugangsdaten in .env eintragen und mit docker compose up -d neu starten.
  2. Unter Verwaltung › Einstellungen im Abschnitt Test-Mail eine Empfängeradresse eintragen und Test-Mail senden wählen.
  3. Kommt die Mail an, lassen Sie Anmeldecode per E-Mail für Lehrkräfte und Admins (zweiter Faktor) angekreuzt.

Der Schalter kann auch abgeschaltet werden, falls der Mailserver ausfällt. Schüler melden sich nie mit Code an, sondern mit der Zugangskarte.

2.7Der Runner: Grenzen und Kapazität

Der Runner kompiliert und startet Java-Programme in einem abgeschotteten Kindprozess, ohne Netz, mit Zeit-, Speicher- und Prozesslimit, schreibgeschütztem Dateisystem und flüchtigem Arbeitsverzeichnis. Er unterstützt Java 21 und 25 und führt außerdem die versteckten Tests der Korrektur sowie die Robo-Testwelten aus.

WasGrenze
Dateien je Laufhöchstens 20, zusammen 1 MB, Namen aus Buchstaben, Ziffern, _ . -
CPU-Zeit je LaufRUNNER_MAX_SECONDS (Standard 10 Sekunden)
Wandzeitinteraktiv 120 Sekunden, bei vorgegebener Eingabe und bei Tests CPU-Zeit plus wenige Sekunden
Java-HeapRUNNER_MAX_MEMORY_MB (256 MB), echter Speicher höchstens Heap plus 384 MB
Threads / Prozesse100 Threads, 40 Prozesse je Lauf
Ausgabe1 MB (bei Tests 256 KB), danach Abbruch mit Hinweis
Platte je Lauf64 MB und 4000 Einträge
ParallelitätRUNNER_MAX_PARALLEL laufende Läufe, weitere warten; höchstens 64 aktive Läufe, darüber Fehler 429

Faustregel: Mit 4 parallelen Läufen und etwa zwei Sekunden je Kompilierung schafft der Runner rund zwei Läufe pro Sekunde. 35 Schüler, die gelegentlich auf Ausführen klicken, sind unkritisch. Wenn eine ganze Klasse gleichzeitig Java startet (zum Beispiel nach einer Durchsage), entstehen kurze Wartezeiten. Dann hilft ein höheres RUNNER_MAX_PARALLEL bei ausreichend CPU-Kernen.

Ehrliche Grenzen der Isolation

Alle Läufe teilen sich im Container einen Benutzer. Ein gezielter Angriff könnte Dateien eines gleichzeitig laufenden fremden Laufs lesen (die Verzeichnisse sind zufällig benannt und gesperrt). Eine Thread- oder Fork-Bombe kann andere Läufe für Sekundenbruchteile stören, der Container selbst bleibt unversehrt. Für Schulklausuren ist das vertretbar; der Runner hat keinen Netzzugang und kann keine Daten nach außen senden. Er ist kein Hochsicherheits-Sandkasten.

2.8Updates

  1. Sichern Sie vorher die Datenbank (2.9).
  2. Neuen Stand holen: bei lokalem Build git pull und docker compose up -d --build, bei GHCR-Images docker compose pull && docker compose up -d.
  3. Datenbankmigrationen laufen beim Start des App-Containers automatisch, abgesichert durch eine Datenbanksperre.
  4. Prüfen Sie /readyz und melden Sie sich einmal an.
Nicht mitten in einer Klausur aktualisieren

Beim Neustart des App-Containers sind die Live-Ansichten für Sekunden nicht erreichbar. Schüler schreiben dank lokaler Sicherung weiter, aber planen Sie Updates außerhalb von Klausurzeiten.

2.9Datensicherung

Zwei Dinge müssen gesichert werden: die Datenbank und das Volume uploads (Material, hochgeladene Dateien, Logo).

# Datenbank sichern docker compose exec -T -e MYSQL_PWD="$DB_ROOT_PASS" db mariadb-dump -uroot klausurwerk > backup.sql # Hochgeladene Dateien sichern docker run --rm -v klausurwerk_uploads:/data -v "$(pwd)":/backup alpine tar czf /backup/uploads.tar.gz -C /data .

Zum Wiederherstellen stoppen Sie die App, spielen den Dump mit mariadb in eine leere Datenbank ein und entpacken das Archiv ins Volume. Der Name des Volumes hängt vom Projektordner ab (docker volume ls).

Einmal vor dem ersten Einsatz proben

Eine Sicherung, die nie zurückgespielt wurde, ist keine. Testen Sie die Wiederherstellung einmal auf einem Testsystem, bevor Sie sich in einer Klausurphase darauf verlassen.

2.10Betrieb und Fehlerbehebung

Alle Container haben Healthchecks und die Einstellung restart: unless-stopped, starten also nach einem Neustart des Servers von selbst. Die Protokolle sind auf 3 Dateien à 10 MB begrenzt.
