Kapitel 2

Installation und Betrieb

Klausurwerk mit Docker Compose aufsetzen, den Setup-Assistenten durchlaufen, den Runner verstehen und die Anwendung dauerhaft betreiben.

Für Admin

2.1Voraussetzungen und Architektur

Klausurwerk besteht aus drei Containern, die gemeinsam mit Docker Compose gestartet werden:

DienstAufgabe
appPHP 8.3 mit Apache. Liefert Oberfläche und Schnittstellen aus, hängt am Netz des Reverse-Proxys (proxy_network) und am internen Runner-Netz. Hört im Container auf Port 80, auf dem Host standardmäßig auf Port 9030.
dbMariaDB 11.4. Alle Daten (Konten, Klausuren, Antworten, Bewertungen) liegen im Volume db_data.
runnerFührt Java-Code (und versteckte Tests) abgeschottet aus. Hängt nur am internen Netz runner_net ohne Internetzugang und ist von außen nicht erreichbar.

Mindestanforderung: 2 CPU-Kerne und 4 GB Arbeitsspeicher für einen Raum mit etwa 35 Schülern. Für mehrere Räume gleichzeitig erhöhen Sie RUNNER_CPUS, RUNNER_MEM_LIMIT und RUNNER_MAX_PARALLEL. Benötigt werden Docker mit dem Compose-Plugin und ein Reverse-Proxy, der das Netz proxy_network bereitstellt und HTTPS terminiert.

Python und SQL laufen im Browser

Nur Java-Aufgaben belasten den Server. Python (Pyodide) und SQL (SQLite als WebAssembly) rechnen im Browser des Schülers. Die Kapazität des Runners ist deshalb nur für Java-Klausuren und die automatische Vorbewertung in der Korrektur relevant.

2.2Erster Start

Mit dem Installations-Assistenten (empfohlen)

Das Skript install.sh erledigt die Einrichtung auf einem Linux-Server mit Docker in einem Durchgang. Es prüft Docker und die Ausstattung des Servers, fragt nach öffentlicher Adresse, Reverse-Proxy, Port, Images, Mailserver und dem ersten Admin-Konto, schreibt die .env mit zufällig erzeugten Passwörtern, legt bei Bedarf das Netz proxy_network an, trägt TRUSTED_PROXIES ein, startet die Container und wartet, bis die Anwendung bereit ist.

git clone https://github.com/TheUnknown-0/klausurwerk.git /opt/klausurwerk cd /opt/klausurwerk sudo ./install.sh

Ohne vorherigen Klon reicht ein Befehl: curl -fsSL https://raw.githubusercontent.com/TheUnknown-0/klausurwerk/main/install.sh | sudo bash. Das Skript fragt dann nach dem Zielordner. Erlaubt sind ein absoluter Pfad, ein Pfad relativ zum aktuellen Ordner (klausurwerk, ../klausurwerk), ein einzelner Punkt für ./klausurwerk und ~/… für das eigene Home-Verzeichnis. Ist der Ordner schon belegt, landet Klausurwerk im Unterordner klausurwerk.

Am Ende zeigt das Skript, was am Reverse-Proxy noch einzurichten ist (siehe 2.4). Die Anwendung ist dann nur auf dem Server selbst erreichbar (127.0.0.1), bis der Proxy-Host steht. Ein zweiter Aufruf erkennt die Installation und bietet an, sie zu aktualisieren (2.8) oder die Einrichtung erneut zu durchlaufen; dabei lässt sich die vorhandene .env behalten.

Alte Datenbank, neue Passwörter

MariaDB übernimmt die Passwörter aus .env nur beim allerersten Start. Wer den Ordner löscht und neu installiert, behält die alte Datenbank (Docker-Volume), aber bekommt neue Passwörter, und die App kommt nicht mehr an die Daten. Der Assistent erkennt das und bietet zwei Wege an: die alte .env zurücklegen (Daten bleiben) oder die alten Daten nach Eintippen von „löschen“ verwerfen.

Warum der Admin auf der Kommandozeile entsteht

Die Einrichtung im Browser (/setup) steht jedem offen, solange es kein Konto gibt. Der Assistent legt das erste Admin-Konto deshalb direkt an, bevor die Domain öffentlich erreichbar ist. Von Hand geht das mit docker compose exec app php bin/setup.php.

Von Hand

  1. Projektordner auf den Server kopieren (oder aus Git klonen) und die Vorlage der Konfiguration kopieren: cp .env.example .env.
  2. In .env die Pflichtwerte setzen: DB_PASS, DB_ROOT_PASS und RUNNER_TOKEN (zum Beispiel mit openssl rand -hex 32). Mit APP_PORT=127.0.0.1:9030 ist der Port nur auf dem Server erreichbar; Docker umgeht Firewall-Regeln wie ufw.
  3. Das Netz des Reverse-Proxys anlegen, falls es noch nicht existiert: docker network create proxy_network.
  4. Bauen und starten: docker compose up -d --build. Der erste Build lädt Basis-Images und Laufzeiten und dauert einige Minuten.
  5. Das erste Admin-Konto anlegen: docker compose exec app php bin/setup.php oder im Browser unter http://localhost:9030 mit dem Setup-Assistenten. Tun Sie das, bevor die Domain öffentlich erreichbar ist.
cp .env.example .env # DB_PASS, DB_ROOT_PASS und RUNNER_TOKEN setzen docker network create proxy_network docker compose up -d --build docker compose exec app php bin/setup.php

Der Setup-Assistent im Browser

Der Assistent erscheint nur, solange es noch kein Konto gibt. Er fragt nach Vorname, Nachname, Benutzername, E-Mail (für Anmeldecodes), Passwort (mindestens 8 Zeichen), Passwort wiederholen und dem Namen der Schule. Damit wird das erste Admin-Konto angelegt. Danach ist die Seite /setup nicht mehr nutzbar, und Sie landen auf der Anmeldeseite. Wurde das Konto mit install.sh oder bin/setup.php angelegt, erscheint der Assistent gar nicht.

Gesund oder nicht?

Prüfen Sie nach dem Start /healthz (antwortet ok, wenn die Anwendung läuft) und /readyz (200, wenn auch die Datenbank erreichbar ist, sonst 503). Beide Adressen funktionieren ohne Anmeldung und eignen sich für Überwachungswerkzeuge.

2.4Reverse-Proxy und HTTPS

Im Betrieb steht ein Reverse-Proxy (zum Beispiel Nginx Proxy Manager, Traefik oder Caddy) vor der Anwendung. Er terminiert HTTPS und leitet auf den Container klausurwerk-app (Port 80) im Netz proxy_network weiter. Wichtig:

  • Tragen Sie die Adresse oder das Netz des Proxys in TRUSTED_PROXIES ein (bei Docker zum Beispiel das Subnetz von proxy_network, nachzusehen mit docker network inspect proxy_network). Erst dann weiß die Anwendung, dass die Anfragen über HTTPS kamen: Sitzungs- und Gerätecookies bekommen das Secure-Flag, QR-Codes und SEB-Dateien die richtige Adresse, und Anmeldedrossel und Audit-Log sehen die echte Adresse der Clients. Ohne den Eintrag sieht die Anwendung nur HTTP.
  • Die Anwendung setzt strenge Sicherheitsköpfe (Content Security Policy, Cross-Origin-Isolation). Der Proxy darf diese Köpfe nicht entfernen oder überschreiben. Ohne Cross-Origin-Isolation kann Python-input() im Browser nicht auf Eingaben warten.
  • WebSockets sind nicht nötig. Die Live-Ansichten arbeiten mit kurzem Abruf (Polling).
  • Tragen Sie unter Verwaltung › Einstellungen die Öffentliche Adresse ein. Sie steckt im QR-Code der Zugangskarten und in der SEB-Datei. Ohne Eintrag wird die Adresse verwendet, mit der Sie gerade zugreifen, auf dem Server oft localhost, was auf den Karten wertlos ist.

2.5Fertige Images aus der GHCR

Statt lokal zu bauen, kann der Server fertige Images aus der GitHub Container Registry ziehen. Setzen Sie in .env:

APP_IMAGE=ghcr.io/theunknown-0/klausurwerk-app:latest RUNNER_IMAGE=ghcr.io/theunknown-0/klausurwerk-runner:latest

und starten Sie mit docker compose pull && docker compose up -d. Die Images entstehen automatisch über GitHub Actions.

2.6Mailserver und Anmeldecode

Lehrkräfte und Admins können sich zusätzlich mit einem sechsstelligen Anmeldecode per E-Mail absichern (zweiter Faktor). Das funktioniert nur, wenn MAIL_HOST und MAIL_FROM_ADDRESS gesetzt sind. Solange das fehlt, zeigt die Übersicht des Admins einen gelben Hinweis, und Lehrkräfte melden sich nur mit Passwort an.

  1. SMTP-Zugangsdaten in .env eintragen und mit docker compose up -d neu starten.
  2. Unter Verwaltung › Einstellungen im Abschnitt Test-Mail eine Empfängeradresse eintragen und Test-Mail senden wählen.
  3. Kommt die Mail an, lassen Sie Anmeldecode per E-Mail für Lehrkräfte und Admins (zweiter Faktor) angekreuzt.

Der Schalter kann auch abgeschaltet werden, falls der Mailserver ausfällt. Schüler melden sich nie mit Code an, sondern mit der Zugangskarte.

2.7Der Runner: Grenzen und Kapazität

Der Runner kompiliert und startet Java-Programme in einem abgeschotteten Kindprozess, ohne Netz, mit Zeit-, Speicher- und Prozesslimit, schreibgeschütztem Dateisystem und flüchtigem Arbeitsverzeichnis. Er unterstützt Java 21 und 25 und führt außerdem die versteckten Tests der Korrektur sowie die Robo-Testwelten aus.

WasGrenze
Dateien je Laufhöchstens 20, zusammen 1 MB, Namen aus Buchstaben, Ziffern, _ . -
CPU-Zeit je LaufRUNNER_MAX_SECONDS (Standard 10 Sekunden)
Wandzeitinteraktiv 120 Sekunden, bei vorgegebener Eingabe und bei Tests CPU-Zeit plus wenige Sekunden

ParallelitätRUNNER_MAX_PARALLEL laufende Läufe, weitere warten; höchstens 64 aktive Läufe, darüber Fehler 429

Faustregel: Mit 4 parallelen Läufen und etwa zwei Sekunden je Kompilierung schafft der Runner rund zwei Läufe pro Sekunde. 35 Schüler, die gelegentlich auf Ausführen klicken, sind unkritisch. Wenn eine ganze Klasse gleichzeitig Java startet (zum Beispiel nach einer Durchsage), entstehen kurze Wartezeiten. Dann hilft ein höheres RUNNER_MAX_PARALLEL bei ausreichend CPU-Kernen.

Ehrliche Grenzen der Isolation

Jeder Lauf bekommt einen eigenen Benutzer (UID aus einem Pool von 64), ein eigenes Arbeits- und Temp-Verzeichnis, das für andere Läufe unlesbar ist, und einen Systemaufruf-Filter (seccomp), der Netzwerk-Sockets und gemeinsame Kanäle zwischen Läufen sperrt. Eine Thread- oder Fork-Bombe trifft nur den eigenen Lauf. Was bleibt: Testcode und Schülercode laufen bei der automatischen Vorbewertung im selben Prozess, ein gezielt präpariertes Programm kann dort ein „bestanden“ vortäuschen. Vorbewertungen sind deshalb immer nur Vorschläge, die die Lehrkraft prüft. Der Runner hat keinen Netzzugang und kann keine Daten nach außen senden.

2.8Updates

Der Installations-Assistent hat einen Update-Modus. Im Projektordner genügt:

cd /opt/klausurwerk sudo ./update.sh

update.sh ist die Kurzform von ./install.sh --update. Auch ./install.sh ohne Zusatz fragt in einer bestehenden Installation, ob aktualisiert, neu eingerichtet oder abgebrochen werden soll. Der Updater geht so vor:

  1. Er holt den neuen Code und zeigt den installierten und den neuen Stand mit der Liste der Änderungen. Wurden Dateien im Ordner von Hand geändert, legt er sie nur nach Rückfrage mit git stash beiseite (zurückholen mit git stash pop).
  2. Bei fertigen Images (GHCR) fragt er die Registry nach neuen Images. Ist weder Code noch Image neu, endet er mit „auf dem neuesten Stand“. Bei lokalem Build bietet er dann nur einen Neubau für Sicherheits-Updates der Basis-Images an.
  3. Er prüft, ob gerade eine Klausur läuft, pausiert ist oder im Warteraum steht, nennt sie und fragt nach, bevor er weitermacht.
  4. Er sichert Datenbank, hochgeladene Dateien und .env nach backups/<Datum-Uhrzeit>/ (nur für root lesbar). Die Sicherung lässt sich überspringen, empfohlen ist sie nicht.
  5. Er wechselt auf den neuen Code, lädt die Images oder baut sie neu, startet die Container und wartet, bis /readyz antwortet. Datenbankmigrationen laufen beim Start des App-Containers automatisch, abgesichert durch eine Datenbanksperre.
  6. Zum Schluss nennt er Einstellungen aus .env.example, die in Ihrer .env fehlen (bis dahin gilt der Standardwert), und bietet an, alte, unbenutzte Images zu löschen.

Melden Sie sich danach einmal an. Stammt das geladene App-Image von einem älteren Stand als der Code, weist der Updater darauf hin: GitHub baut die Images nach jeder Änderung neu, das dauert etwa zehn Minuten. Starten Sie das Update dann später noch einmal.

Ältere Installationen

Kennt das vorhandene install.sh den Update-Modus noch nicht, laden Sie beim ersten Mal das aktuelle Skript direkt: curl -fsSL https://raw.githubusercontent.com/TheUnknown-0/klausurwerk/main/install.sh | sudo bash -s -- --update. Es findet den Ordner einer laufenden Installation selbst.

Zurück auf den alten Stand

Den alten Stand nennt der Updater in seiner Zusammenfassung. Code zurücksetzen mit sudo git checkout <alter Stand>, bei lokalem Build danach sudo docker compose up -d --build. Bei GHCR-Images in der .env das passende Image mit Kennung wählen, etwa APP_IMAGE=ghcr.io/theunknown-0/klausurwerk-app:sha-abc1234 (ebenso RUNNER_IMAGE), dann sudo docker compose up -d. Hat das Update die Datenbank migriert, spielen Sie die Sicherung aus backups/ zurück (2.9). Mit git checkout main und dem Updater geht es später wieder nach vorn.

Von Hand geht ein Update weiterhin so: Datenbank sichern (2.9), dann bei lokalem Build git pull und docker compose up -d --build, bei GHCR-Images git pull, docker compose pull und docker compose up -d.

Nicht mitten in einer Klausur aktualisieren

Beim Neustart des App-Containers sind die Live-Ansichten für Sekunden nicht erreichbar. Schüler schreiben dank lokaler Sicherung weiter, aber planen Sie Updates außerhalb von Klausurzeiten.

2.9Datensicherung

Zwei Dinge müssen gesichert werden: die Datenbank und das Volume uploads (Material, hochgeladene Dateien, Logo).

# Datenbank sichern docker compose exec -T -e MYSQL_PWD="$DB_ROOT_PASS" db mariadb-dump -uroot klausurwerk > backup.sql # Hochgeladene Dateien sichern docker run --rm -v klausurwerk_uploads:/data -v "$(pwd)":/backup alpine tar czf /backup/uploads.tar.gz -C /data .

Zum Wiederherstellen stoppen Sie die App, spielen den Dump mit mariadb in eine leere Datenbank ein und entpacken das Archiv ins Volume. Der Name des Volumes hängt vom Projektordner ab (docker volume ls).

Der Updater (2.8) legt vor jedem Update eine Sicherung in backups/<Datum-Uhrzeit>/ an: datenbank.sql.gz, uploads.tar.gz und eine Kopie der .env unter dem Namen env. Den Dump spielen Sie gepackt ein, das Archiv entpacken Sie über den App-Container:

sudo docker compose stop app gunzip -c backups/DATUM/datenbank.sql.gz | sudo docker compose exec -T db sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mariadb -uroot "$MYSQL_DATABASE"' sudo docker compose run --rm --no-deps -T --entrypoint tar app xzf - -C /var/www/html/uploads < backups/DATUM/uploads.tar.gz sudo docker compose up -d

Die Sicherungen sammeln sich an. Alte Ordner unter backups/ löschen Sie bei Bedarf von Hand; der Updater weist ab sechs Sicherungen darauf hin.

Passen Datenbank und Dateien nach einer Wiederherstellung nicht mehr zusammen, bleiben unter uploads/ Dateien ohne Datenbankzeile zurück. docker compose exec app php bin/cleanup.php listet sie, mit --delete werden sie gelöscht (Dateien jünger als eine Stunde bleiben unangetastet, jeder Lauf steht im Audit-Log). Beim Löschen einer Klausur oder eines Schülerkontos räumt die Anwendung Material und hochgeladene Antwortdateien selbst weg.

Einmal vor dem ersten Einsatz proben

Eine Sicherung, die nie zurückgespielt wurde, ist keine. Testen Sie die Wiederherstellung einmal auf einem Testsystem, bevor Sie sich in einer Klausurphase darauf verlassen.

2.10Betrieb und Fehlerbehebung

Alle Container haben Healthchecks und die Einstellung restart: unless-stopped, starten also nach einem Neustart des Servers von selbst. Die Protokolle sind auf 3 Dateien à 10 MB begrenzt. Die Übersicht zeigt Admins oben Hinweise, wenn etwas fehlt: Mailserver nicht eingerichtet, RUNNER_TOKEN leer, Runner nicht erreichbar, öffentliche Adresse nicht hinterlegt oder Aufbewahrungsfristen überschritten.
